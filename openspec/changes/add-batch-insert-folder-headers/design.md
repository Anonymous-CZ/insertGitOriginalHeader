## Context
当前扩展按“单文件”插入文件头：读取 Git 原始作者/日期，按文件类型选择注释风格，并在文件顶部写入模板。

批量补齐会引入新的问题域：
- 文件扫描与过滤（性能、排除规则）
- 已有文件头识别（避免重复插入或误伤其他工具生成的头）
- UI 交互（扫描确认、进度、取消、结果报告）
- 并发与 Git 调用压力（避免同时对大量文件执行 git 命令）

## Goals
- 在不改变单文件插入语义的前提下，为“文件夹批量补齐缺失文件头”提供一条端到端可用路径
- 默认行为尽量安全：避免处理二进制/不支持注释的文件，避免重复插入
- 性能可控：限制并发，提供取消

## Non-Goals
- 不提供“回滚/撤销批量插入”的专用功能（依赖用户使用 Git 或编辑器撤销）
- 不尝试识别/兼容所有第三方文件头模板，仅保证本扩展生成的模板可被识别
- 不引入新 UI 页面或复杂交互（保持弹窗/进度条/结果提示）

## Decisions
- Scanning
	- 优先使用 VS Code API 进行文件枚举（例如 `workspace.findFiles`），并在扫描阶段应用默认排除与用户排除模式
	- 仅对文本文件打开/读取必要的前 N 行用于检测，避免一次性读取大文件
- Header detection
	- 仅检测“本扩展生成的文件头特征字段”是否出现在文件前 `commentCheckLines` 行内
	- 默认以 `@Author` + `@Date` + `@FilePath` 的组合判断为“已包含文件头”，以降低误判概率
- Processing
	- 使用受控并发队列，最大并发由 `batchConcurrency` 限制
	- 每个文件复用单文件插入路径，确保字段语义与注释风格选择一致
- UX
	- 先扫描再确认，再执行；执行时使用 `withProgress`，支持取消 token
	- 完成后给出汇总结果；可选生成文本报告并允许一键复制

## Alternatives Considered
- Node.js 自行递归遍历文件系统
	- Pros: 不依赖 VS Code 的 glob
	- Cons: 需要自行处理 ignore/权限/符号链接/性能，且多根工作区语义更复杂
- 基于 git ls-files 进行扫描
	- Pros: 可以天然限制在 Git 跟踪文件
	- Cons: 无法覆盖未跟踪但仍需补齐的文件；也不适用于非 Git 场景

## Risks / Trade-offs
- 误判“已有文件头”导致跳过
	- 缓解：提升检测条件（字段组合）、可配置 `commentCheckLines`、提供“显示详情”让用户确认
- Git 命令大量执行导致卡顿
	- 缓解：并发限制、取消、进度提示

## Migration Plan
- 新增命令与设置项为向后兼容的增量变更；不影响现有单文件命令。
